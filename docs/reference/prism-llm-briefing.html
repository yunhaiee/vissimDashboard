Putting an LLM inside the Vissim dashboard

How LLM↔simulation integration actually works, how research teams and companies have built it, what Prism should do — and the papers to know, prepared for the discussion with Prof. Inhi Kim.

Prepared 2026-07-20 · researched & verified from primary sources · all links live
01The short answers

Three things to walk in knowing

Is chat-next-to-sim possible?

Yes — and it is the correct design. The user never opens Vissim. Vissim runs headless on Dochak's Windows servers; the dashboard re-renders Vissim's data (network geometry, vehicle positions, KPIs) on the web page, with the chat panel beside it. Nobody needs a local Vissim install. Dochak's own Vista product already streams live Vissim vehicle trajectories out of the app — proof the hard part is solved in-house.

How is this built?

Every serious integration works the same way: the LLM emits structured tool calls (JSON like set_lane_count(link=12, lanes=4)), and ordinary backend code executes them against the app's scripting API — for Vissim, the COM API. MCP is a standard plug format for exposing such tools to third-party AI apps. Since Prism owns both the chat and the simulation servers, plain tool calling is the right layer; MCP can be added later as an external interface.

Which paper did he mean?

Almost certainly ChatSUMO Agent (Transportation Research Part C, 2026 — the field's top journal) or AgentSUMO (KAIST, from his own graduate school, submitted to the same journal). Both let non-experts create and edit traffic simulations by chatting. Both use SUMO. Nobody has published the Vissim version — that space is open for Dochak.

02Mechanics

How an LLM "edits" a simulation — the agent loop

The most common misconception: the AI does not see the screen or click buttons in Vissim. What actually happens is a text-only negotiation called tool calling (or function calling). You describe a menu of allowed operations to the model in JSON Schema; the model replies with which operation to run and with what arguments; your own code performs it and reports back. The model is a planner — your backend is the hands.

1 · PROMPT
User asks
"What happens with 4 lanes instead of 3?"
2 · PLAN
LLM picks tools
Emits clone_scenario(), set_lane_count(link, 4), run_simulation(seeds=3)
3 · EXECUTE
Backend runs them
Python drives Vissim through COM; results come back as data
4 · OBSERVE
LLM reads results
Delay, queue length, throughput per scenario
5 · ANSWER
Plain-language reply
"Average delay drops 18%; the bottleneck moves to the next junction."
Steps 2–4 repeat in a loop until the task is done — that loop is what makes it an "agent." Both the Anthropic Messages API and the OpenAI Responses API run this natively. (Note: the older OpenAI Assistants API is deprecated, sunset 2026-08-26 — don't build on it.)

So where does MCP fit?

MCP (Model Context Protocol) standardizes the packaging of those tools so that any AI client — Claude, ChatGPT, Copilot, Cursor — can discover and call them without custom code. Originally from Anthropic, it was donated to the Linux Foundation's Agentic AI Foundation in Dec 2025 (backed by OpenAI, Google, Microsoft, AWS) and is now the industry standard, with ~10,000+ public servers. It has two transports: stdio for a server running on the user's own machine (the Blender/Fusion desktop pattern) and Streamable HTTP for hosted remote servers (the Figma pattern).

The key judgment call, and the practitioner consensus in 2026: MCP solves the "many clients × many tools" interoperability problem. A product that owns both its chat UI and its tools — like Prism — doesn't have that problem, and plain tool calling against an internal API is simpler, faster, and easier to secure. You expose an MCP endpoint later if customers want to drive Prism from their own AI assistants.

03Landscape

How research teams and companies each built it

Two worlds to compare: research systems that edit traffic simulations from natural language (all SUMO-based, because SUMO is free and open), and commercial products that put AI inside professional desktop software (Premiere, Fusion 360, Figma, Blender). The pattern that repeats across both is the useful thing to cite tomorrow.

The repeating pattern: curated, bounded tools beat "run any script." Every mature integration (Adobe's, Fusion's, Unity's ~47 tools) converged on a fixed menu of well-described operations, because agents are dramatically more reliable when the action space is explicit — and because you can validate each operation before it touches the model.

04Reading list

The papers, and what to take from each

ChatSUMO Agent: An LLM-Based Agent for Conversational Traffic Simulation in SUMO

Transportation Research Part C · 2026
Shuyang Li, Talha Azfar, Ruimin Ke — Rensselaer Polytechnic Institute
PaperCode (MIT)

The closest published system to the Prism vision, in the field's most prestigious journal — the likely "top journal paper." A closed-loop agent takes natural language through the full workflow: network generation, demand creation, simulation execution, KPI analysis, and iterative modification of scenarios.

Notice for your development
  • How they decompose the work into tool modules (network / routing / simulate / analyze / modify) — this is the tool menu design problem you'll face for Vissim.
  • The agent updates its internal state after each tool result — that's what makes multi-turn "now also change X" conversations work.
  • The repo is small, Python + Streamlit + OpenAI API. Read it end-to-end; it's the cheapest way to understand the whole loop.

AgentSUMO: An Agentic Framework for Interactive Simulation Scenario Generation in SUMO via LLMs

arXiv 2511.06804 · KAIST · under review at TR Part C
Minwoo Jeong, Jeeyun Chang, Yoonjin Yoon — KAIST Cho Chun Shik Graduate School of Mobility (Prof. Kim's school)
Paper

From colleagues in Prof. Kim's own graduate school — he very likely knows this work directly. Targets non-expert users (planners, officials): an Interactive Planning Protocol interprets vague goals, assesses task complexity, asks clarifying questions, and fills in missing parameters before running anything; MCP handles tool orchestration underneath. Demonstrated on Seoul and Manhattan networks.

Notice for your development
  • Their central finding is a UX finding: non-experts write under-specified prompts, so the agent must clarify before executing. That dialogue design is squarely your job as the UX owner.
  • The complexity-assessment step (simple edit vs. multi-step study) maps directly to how Prism should decide between "just apply it" and "propose a plan first."
  • Citing this tomorrow signals you did your homework — it's the in-house reference point.

ChatSUMO: LLM for Automating Traffic Scenario Generation

IEEE Open Journal of Vehicular Technology · 2024
arXiv 2409.09040
Paper

The first mover. A simpler pipeline (not a loop): user text → keyword extraction → Python scripts build a SUMO network from OpenStreetMap → run → report. Handles edge edits, lane changes, and traffic-light adjustment for a real city (Albany).

Notice for your development
  • Read it for the limits: a fixed pipeline can't recover from errors or handle follow-ups — the reason the field moved to agent loops within a year.

SUMO-MCP: Leveraging the Model Context Protocol for Autonomous Traffic Simulation

arXiv 2506.03548 · 2025
Paper

Wraps SUMO's utility toolchain into a single MCP server so a general-purpose AI client can generate scenario batches, run them, and optimize signal timing from chat.

Notice for your development
  • This is the template for a future "Vissim-MCP" — which does not exist publicly anywhere. If Dochak wants a paper of its own, this gap is the opening.

TrafficSimAgent: Hierarchical multi-agent orchestration over simulator MCP tools

arXiv 2512.20996 · 2025
Paper

An orchestrator agent decomposes the task and delegates to executor sub-agents, with simulator API functions exposed as MCP tools. Aims at simulator-agnostic automation.

Notice for your development
  • Skim only. Multi-agent hierarchies are v3 territory; its motivation section is a good survey of the space.
05Your question

Can the simulation live on the page, with chat beside it?

Yes. The mental shift: you never embed Vissim itself — you embed a view of Vissim's data. Vissim is a Windows desktop program with no web version, but when driven through COM it runs headless on a server and everything it knows is readable as data: network geometry from the .inpx file (it's XML), vehicle positions every timestep, and all evaluation results. The dashboard re-draws that data in the browser — which Prism already does for validation views. The alternative you worried about (each user opening a locally installed Vissim with some AI bolted on) is the desktop-app pattern from Blender/Fusion — it's only necessary when the software runs on the customer's machine. Prism hosts Vissim, so it isn't.

Select first, then ask — the map as an input device

The mockup shows the user having clicked a road before typing, so the prompt says "here" rather than naming a street. This is worth building early, because it dissolves the hardest problem in the system: working out which objects the user means. A Vissim network is hundreds of numbered links with no useful names, so "widen the main road" forces the agent to search, guess, and often guess wrong. A selection removes the guess entirely.

Three things fall out of it at once. Grounding: on selection you hand the model a factual summary — link 12, three lanes, 240 metres, signalised junction with a 90-second cycle, node evaluation armed — so it reads rather than infers. Fewer steps: the agent goes straight to the edit instead of burning turns on discovery, which matters most for the weaker models an on-premise deployment would use. A visible scope: what's highlighted is what can change, so the blast radius is on screen before anything runs.

That last point converges with the reference registry the architecture already needs: selection → enumerate everything attached → highlight it. The selection interface and the safety mechanism are the same machinery, which is the strongest argument for building it in v1 rather than treating it as polish.

Design the selection types around what the tools can do, not around geometry. Selecting an intersection offers signal timing and turn restrictions; a corridor offers speed limits, lane counts and coordination; an area offers read-only questions and demand scaling. Narrowing the menu to what the selection supports is itself a reliability gain — the model chooses among four relevant tools instead of twenty.

Two cautions. Selection is not the same as the affected set: changing a link's lane count also touches its connectors, routes, conflict areas and signal heads, so the interface must show what it will reach beyond the highlight, or it promises a containment it can't deliver. And some changes are inherently wider than any selection — signal cycle time is a corridor property, so selecting one junction and changing it has to escalate to every coordinated intersection or be refused. The system needs to be able to say "you selected one junction; this affects five."

On 2D versus 3D: make the 2D map the working surface and Vista the review surface. Topology is legible in plan view and picking a specific lane in a perspective 3D scene is fiddly — but 3D is where a non-expert recognises a place, and it is far better for showing a stakeholder the before-and-after. Sync the selection between them. One integration requirement to raise early with whoever owns Vista: the rendered geometry must carry Vissim object IDs through to the client, or clicking a road in 3D can't resolve to a link.

Three layers. The middle one — a curated simulation API — is the load-bearing decision: it serves the normal UI buttons and the AI agent, it's where edits get validated before touching Vissim, and it's the thing you'd wrap in MCP later if third-party access is ever wanted.

  • Vissim workers: one Vissim process per active session, driven by Python over COM (Python has shipped embedded in Vissim since the 2023 version). COM is effectively single-threaded per instance, so commands go through a per-session queue — the identical constraint every Fusion 360 integration hit.
  • Copy-on-write scenarios: never edit the user's model in place. Clone the .inpx, apply the change, run, keep the original for the comparison view. This makes "what if" free and undo trivial.
  • Curated verbs, not scripts: get_network_summary, set_lane_count, set_desired_speed, set_vehicle_input, set_signal_timing, run_simulation → job_id, get_results, compare_scenarios. Each validates its inputs and returns a structured diff.
  • Approve-before-run: the agent proposes; the dashboard renders the diff; the human clicks. This is both the safety story and — per AgentSUMO — what non-expert users actually need.

07Details that matter

Technical facts to have ready

  • The COM API is the official automation surface. It can load models, set vehicle inputs (demand), desired-speed decisions and distributions, signal timings, run simulations with or without the GUI, and read every evaluation result. PTV's COM knowledge base and the BME Traffic Lab COM manual are the starting points.
  • Open question to verify once you have the code: lane edits. Changing speeds/demand/signals via COM is routine; adding a lane may require editing the .inpx file directly and reloading. Since .inpx is plain XML, this is very doable either way — but it decides your v1 scope. Suggested phasing: v1 = parameter edits (speed, demand, signals), v2 = geometry edits (lanes).
  • Licensing is the hidden cost driver. Each concurrent Vissim instance consumes a license seat. Worker pooling and queueing aren't just engineering hygiene — they're what caps license spend.
  • One run is not an answer. Microsimulation is stochastic; a scenario comparison needs several runs with different random seeds, averaged. Build "3 seeds by default" into run_simulation and show the spread — this is also what makes the AI's claims defensible to engineers.
  • Runs take minutes, so everything is async. run_simulation returns a job id; the dashboard subscribes to progress over WebSocket. (MCP's new "tasks" feature imitates exactly this — you get it for free with your own job queue.)
  • Guardrails live in the API layer, not the prompt. Range-check every value (no 200 km/h streets), whitelist editable objects, and log every mutation with who/what/when. The LLM proposes; validated code disposes.
  • On-premise LLM may come up. Dochak markets Nexus as "100% on-premise" for a reason — Korean public agencies often can't send data to foreign clouds. Keep the agent loop provider-agnostic (clean tool schemas work with Claude, GPT, or a local open-weights model) so an on-prem variant stays possible.
  • The AI is the cheap part. Model APIs bill per token and development traffic is tiny — a scenario-editing turn is a few thousand tokens, so hundreds of test runs cost single-digit dollars. Two levers cut it further in production: prompt caching (the tool definitions are a fixed prefix, so repeat calls read them at roughly a tenth of normal input cost) and the batch API (half price for overnight evaluation runs). Vissim licences and GPU hardware are the real cost lines, not the model.
08Where the difficulty actually is

The two hard problems, explained from scratch

Neither adapter is the hard part, and neither is the AI. The difficulty sits in the shared core library, in two places: changing road geometry and knowing what a user's words should change. Both are worth understanding in plain terms, because both are as much design problems as engineering ones.

Problem one — a lane is not a number you can set

The intuitive mental model is that a road in Vissim has a property called "lanes" that holds 3, and you change it to 4. That is not how the file works. A Vissim network is a graph assembled from pieces: short stretches of road called links, stitched end-to-end and corner-to-corner by connectors. Lane count is fixed when a link is built — the COM method AddLink takes a LaneWidths array with one entry per lane. Four lanes means an array of four widths, decided at construction.

A designer's analogy: it's less like changing a text layer's font size and more like changing an artboard's column count in a layout where every element is pinned to specific columns. You can't nudge the number — you rebuild the grid, and everything anchored to the old one comes loose.

And a great deal is anchored to a link. Changing it means finding and re-attaching all of it:

flowchart TD
  L["LINK 12
3 lanes"]
  C1["Connectors
attached to specific lane numbers"] --> L
  C2["Routing decisions

  C3["Signal heads & detectors

  C4["Conflict areas & priority rules

  C6["Vehicle inputs & measurement points

So set_lane_count is really: read the whole neighbourhood around the link, rebuild the link with a new lane array, re-attach every referencing object to the right lane and position, and re-derive the things Vissim normally computes for you. That's an algorithm to design, not a wrapper to write.

It also isn't fully specified by the user's request. "Make it 4 lanes" leaves open: which side does the new lane go on, does it run the full length or taper, and what happens where the link ends — does the next link get a lane too, or does this become a merge? A human engineer answers these from context in seconds. Software has to either ask or decide.

The failure mode that matters most

A broken network still runs. If the rebuild silently drops a connector, Vissim doesn't crash — vehicles just quietly stop being able to reach part of the network, and the simulation finishes and reports confident-looking numbers that are wrong. A traffic engineer might notice the throughput looks off. Prism's target user — a non-expert who came here precisely because they can't read Vissim — cannot. Every safeguard below exists to catch this class of error before a number reaches the screen.

How to get through it

  • Check whether the lane already exists. Many production models already contain the extra lane and restrict it (bus-only, closed, vehicle-class limited). Opening an existing lane is an attribute change — easy and safe. Detect that case first; it may cover a real share of "add a lane" requests without any geometry work.
  • Build a reference registry. Before editing, enumerate every object pointing at the link and store it. After editing, assert every one landed somewhere valid. This registry is the core algorithm — write it once, and it also powers your undo, your diff view, and your "what will this affect?" preview.
  • Refuse gracefully, don't fail silently. Support the simple topology first (a mid-block link, uniform lane widths, straightforward connectors). When the model doesn't match, say so plainly: "This junction is too complex for me to modify safely — here's what I can change instead."
  • Smoke-test every edit. Run 30 seconds of simulation before the real runs and check invariants: vehicles entering ≈ vehicles arriving, nothing stranded, no link that used to carry flow now carrying zero. Cheap, and it catches the silent-breakage class directly.
  • Keep golden models. A handful of small test networks in the repo, with a known-correct result for each edit. Every change to the core library runs against them. This is the difference between a library people trust and one they don't.
  • Show the change visually. Copy-on-write means the original is always intact, so you can render before/after geometry side by side on the map. A human spotting "wait, that lane goes the wrong way" is your last and best line of defence.

Problem two — "70 km/h" doesn't name one thing

This one looks easy and isn't. Vissim models speed with several distinct concepts, and a plain request maps to more than one of them:

  • Desired speed distribution — a curve, not a number. Real drivers don't all drive the limit, so Vissim stores a spread. Each vehicle draws a percentile when it enters and keeps that percentile for its whole trip: a "40th-percentile driver" stays a 40th-percentile driver everywhere.
  • Desired speed decision — a marker placed at a point on a lane. Crossing it assigns the vehicle a new distribution, and the speed changes from there on. This is how a speed-limit change is modelled.
  • Reduced speed area — a zone, where vehicles slow down in advance so they're already at the lower speed on entry, then resume afterwards. This is how curves and turns are modelled — not speed limits.

So "the simulation ran at 60, what about 70?" could mean: swap the distribution at an existing decision point, add a decision point that doesn't exist yet, change the network's default, or adjust a reduced-speed area. Each produces different numbers. All of them produce plausible numbers. And going from 60 to 70 is not "add 10" — a real engineer substitutes a differently-shaped distribution, because the spread of driver behaviour changes with the limit too.

The deeper difficulty: this knowledge is tacit. Your engineers apply it by habit and have never had to write it down, so it doesn't exist as a document you can read — it has to be extracted from people. And the LLM will not flag its own uncertainty here; it will pattern-match to the most common-looking option and state the result with total confidence.

How to get through it

  • Run elicitation sessions, time-boxed. Sit with Dr. Chun or Dr. Oh and screen-record them performing ten real edits while narrating why. Each one becomes a validation rule plus a test case. Three sessions will get you most of the way; it's far cheaper than discovering the rules through wrong results months later.
  • Encode the rules as code, not prompt text. A prompt is a suggestion the model may ignore; a check in the API layer is enforcement. Anything that must always hold belongs in the validation layer.
  • Introspect each model on upload, then constrain what's offered. Scan what the model actually contains and only expose edits that make sense for it. If a link has no desired speed decision, don't offer to change one — offer to add one, explicitly.
  • Make ambiguity a conversation, not a guess. When a request maps to more than one object, the agent asks: "the whole corridor, or just this approach?" This is exactly AgentSUMO's published finding — and it is a UX design problem, which puts it in your hands.
  • Name the object in the confirmation. Not "changing speed to 70" but "Desired speed decision #14 (northbound, lanes 1–3): distribution 60 urban → 70 urban." An engineer reviewing can catch an error instantly; a non-expert at minimum sees that something specific and checkable happened.
  • Log every mutation. When a client disputes a result six months later, the audit trail of exactly which objects changed is what settles it — and it doubles as your evaluation data if this becomes a paper.
The pattern behind both problems

In both cases the technical difficulty and the UX difficulty are the same difficulty. The system has to know what it doesn't know — that a geometry edit is too complex to do safely, or that a request could mean three things — and then say so usefully instead of guessing. Confident wrong answers are the one outcome that would sink a product aimed at people who can't check the work.

09Deployment variant

If customers require on-premise LLMs

Realistic for Korean public agencies, and Dochak already markets Nexus as fully on-premise. The good news: the architecture doesn't change shape. Layers 1 and 2 are untouched — Vissim already runs on servers you control, so "on-premise" means shipping the whole appliance to the customer's data centre rather than redesigning it. The tool definitions, the validation rules, the job queue, the approve-before-run flow: all identical.

LayerCloud tierOn-premise tier
Vissim workersUnchanged — and licences become the customer's, which simplifies your seat problem

The single code change is a provider interface — keep the agent loop behind a thin abstraction and avoid coupling to vendor-specific features, and switching backends is a base-URL and model-name change. This is the practical reason not to build on provider-proprietary extras.

What genuinely gets harder

  • Tool-calling reliability drops — but far less than it used to. Top open-weight models now sit within a few points of frontier APIs on function-calling benchmarks. The gap that remains shows up where it hurts most here: long multi-step loops, choosing among similar-looking tools, and recovering after a failed step.
  • So move agency from the model into code. Fewer and more distinct verbs; classify the user's intent and run a templated plan rather than letting the model free-form its way through ten steps; use grammar-constrained decoding so the JSON is always structurally valid. Less improvisation, more deterministic orchestration.
  • Evaluation stops being optional. Two backends mean two behaviour profiles, and the only way to know the on-prem tier works is a test suite of prompts mapped to expected tool calls. Build it from day one — it is also, conveniently, the evaluation a paper needs.
  • Ops becomes a product surface: GPU sizing, weight distribution and updates, quantisation choices, and checking each model's licence actually permits commercial redistribution.
  • Korean matters for model choice. Agency users will prompt in Korean, and Korea's sovereign-AI push means some procurements may favour or mandate a domestic model. Supporting one is a competitive advantage, not just a constraint.
The design already hedges this

Two earlier decisions pay off precisely here. Bounded curated verbs matter more with a weaker model, because a small clean action space is what such models handle well. And approve-before-run means every mutation passes a human before executing — so a less reliable model produces a rejected proposal rather than a wrong result. The safety design absorbs most of the capability drop.

One reframe rather than a change: an air-gapped deployment removes the "external AI clients call our hosted MCP" story — but a local MCP endpoint on the appliance becomes the natural way a customer's own internal AI platform talks to Prism. Same adapter, different door.

Recommendation: build cloud-first, but put the provider interface and the evaluation suite in from the start. Then on-premise is a deployment variant and a pricing tier, not a rewrite.
