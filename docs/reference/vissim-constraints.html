What Vissim will let you break without telling you

Every constraint, hidden coupling, and domain rule an automated editing layer has to respect — catalogued from PTV's documentation, its COM reference, and eight state DOT modeling manuals.

Compiled 2026-07-21 · attribute names verified against the PTV Vissim COM reference
The one thing that shapes the whole design

Vissim almost never refuses a bad edit. It runs, finishes, and reports confident numbers. A missing right-of-way rule lets cars drive through each other. A signal plan with conflicting greens produces better delay. Vehicles that can't merge are deleted after 60 seconds and the demand silently disappears. Demand that exceeds capacity waits outside the network and never arrives.

Almost nothing in this catalogue throws an error. That means the validation layer isn't a nice-to-have around the edges of the product — it is the product. Anyone can wire an LLM to the COM API in a week. Knowing which edits are lies is the part that takes real work, and it's the part a competitor can't copy from a blog post.

01Silent failure

Edits that produce confident, wrong answers

Read this section first. Each of these degrades results without any warning, and several of them make the numbers look better, which means an optimising agent will actively seek them out.

Conflict areas default to inactive

silent

Vissim auto-detects where two links overlap and creates a "conflict area" — but its default status is Passive, meaning no right-of-way control at all. Vehicles drive straight through one another. Virginia DOT lists this under "Common Coding Errors": check that vehicles are not running over each other where links cross. In PTV's own shipped example networks, roughly 78% of all conflict areas are Passive.

Worse for an editing tool: conflict areas cannot be created or deleted through the COM API — the container has no add or remove method. They are derived from geometry, and any geometry edit destroys their configuration silently. PTV states that on network re-import, "conflict areas are not retained."

DoSnapshot every conflict area's settings keyed on the link pair (never on its number — see §3), re-apply after any geometry edit, and make "count of Passive conflict areas" a regression metric that must not increase.

Conflicting greens are allowed, and score well

silent

Intergreen matrices (the clearance time required between one movement ending and a conflicting one starting) are checked and highlighted, but never enforced. PTV states plainly that intergreens "cannot be calculated, they can only be entered," and that no validity checks are performed. A plan that gives two conflicting movements green simultaneously will simulate — and because the vehicles pass through each other rather than colliding, the reported delay improves.

This is the single most dangerous interaction in the whole system: an agent asked to "reduce delay at this intersection" has a physically lethal solution available to it that its objective function rewards.

DoValidate every proposed signal plan against the intergreen matrix in your own code before it ever reaches Vissim. Treat a delay improvement larger than expected as a signal to check for a safety violation, not a success.

Vehicles that can't change lanes are deleted

silent

A vehicle that needs to change lanes to follow its route, and reaches the last possible point without finding a gap, waits — and after DiffusTm seconds (default 60) Vissim removes it from the network entirely. This is deliberate, to stop one stuck vehicle gridlocking everything, but it means demand quietly evaporates and downstream volumes fall.

Maryland's DOT is blunt about the consequence of tuning this down: if reviewers see frequent vehicle removals, "the reviewers will likely reject the model." Both Maryland and Washington State raise the default to 200 seconds specifically so that removals become visible rather than routine.

DoNever lower this value automatically. Parse the .err file after every run and surface removal counts as a first-class result, not a log line.

Demand that never enters the network

silent

If you raise traffic beyond what a link can accept, the extra vehicles don't error — they queue outside the network waiting for space. Vissim tracks this as latent demand. A user who asks for "20% more traffic" may get 8% more traffic and a result that looks like the road copes fine.

DoRead the network-wide latent demand measure after every run. If it rose above zero, the requested scenario did not actually happen and the comparison is invalid — say so rather than reporting the numbers.

A gridlocked movement can report the best possible grade

silent

Vissim's level-of-service grade A covers the case of "no volume, as no vehicle is moving, also due to traffic jam." A movement so blocked that nothing gets through reports the same grade as a movement with no delay at all.

DoNever report a level-of-service letter without the throughput next to it. Flag any grade A with near-zero volume as a probable failure, not a success.

Broken routes stay broken even after you fix the road

silent

Routes are stored as fixed sequences of links. PTV: when you split or delete links that a route runs across, those routes become disconnected — "even if you subsequently insert new links or connectors there, these routes remain disconnected." There is a "check and repair all routes" function, but it finds new paths rather than restoring the original ones, so a repaired route may take a completely different course.

DoSnapshot the link sequence of every affected route before a geometry edit, and after repair diff the new sequence against the old. Present any changed route to the user as a change requiring approval.

Deleting a route silently bans a turn

silent

In Vissim a banned movement is expressed by absence — a turn is prohibited when no route covers it, provided routes exist for at least one other movement at that point. So removing the last route through a movement doesn't just remove traffic, it makes that turn illegal.

DoBefore deleting any route, check whether it is the last one covering its movement, and warn explicitly that the turn will close.

Stale route files reused without complaint

silent

Models using dynamic assignment (where drivers choose routes rather than following fixed ones) store converged paths in external files. After a network edit, those files are stale — but Vissim only checks them if a "check edges" option is enabled. Leave it off and it silently reuses paths that no longer match the network.

DoDetect dynamic assignment on model upload. After any geometry edit, regenerate the node-edge graph and delete the path and cost files rather than trusting them.

Writing a parameter the active model ignores

silent

Every driving-behaviour set stores parameters for both car-following models (Wiedemann 74 and 99) regardless of which is active. Urban behaviour uses model 74; freeway uses 99. Writing a model-99 parameter on an urban behaviour changes nothing at all — and nothing reports the no-op, so the agent will confidently announce a change that didn't happen.

DoCheck which car-following model a behaviour uses before writing any of its parameters, and reject mismatched writes as an error rather than letting them pass.
02Not editable how you'd expect

Where the obvious operation doesn't exist

These are the cases where the natural mental model — "find the property, set the value" — has no corresponding operation in Vissim at all.

There is no lane-count property

domain

Lane count is fixed when a link is constructed — the creation call takes an array of lane widths, one entry per lane. To change it you rebuild the link and re-attach everything anchored to it. Compounding this: a link's geometry is read-only, and you cannot add or remove its shape points, so any non-trivial reshape becomes delete-and-recreate too.

DoCheck first whether the extra lane already exists but is restricted (bus-only, closed to a vehicle class) — opening a lane is a simple, safe attribute change and may cover a real share of requests.

There is no speed limit

domain

Links have no speed attribute of any kind. Speed comes from a desired speed distribution — a spread of free-flow speeds from which each vehicle draws a percentile on entry and keeps it for its whole trip. Three different objects can change it, and picking the wrong one gives plausible but wrong numbers:

Changing the composition's distribution changes the speed vehicles enter the network with. A desired speed decision is a marker at a point that changes speed from there onward. A reduced speed area is a zone where vehicles slow in advance and then resume — for curves and turns, not speed limits.

DoTreat any speed request as ambiguous until resolved with the user. Never guess between the three.

A speed decision is permanent unless you undo it

silent

PTV is explicit: to model a temporary speed change with decisions "you must define a second desired speed decision immediately after this, so that the vehicles are given their original desired speed." A tool that adds one marker to model a 30 km/h zone slows vehicles for the entire rest of the network.

DoAlways create speed decisions in pairs, or use a reduced speed area where the change should be bounded.

The main calibration parameter isn't a number

blocks

CC1 — the headway parameter that dominates capacity in the freeway car-following model — is a reference to a separate distribution object, not a scalar. Writing a number to it fails. You either point it at a different distribution or edit that distribution's mean, and distributions are shared, so editing one changes everything referencing it.

DoCreate a new distribution rather than mutating a shared one, and treat every reference-typed attribute as a pointer, not a value.

Signal timings may be outside the API entirely

blocks

How reachable a signal plan is depends entirely on the controller type. Fixed-time plans store cycle time, offsets and green windows in an opaque blob attribute on the controller with no documented per-field access. Ring-Barrier controllers keep theirs in an external .prbc file; VAP controllers in a separate text program; Econolite controllers in a vendor database edited through the vendor's own tool. For those, the signal logic is genuinely outside anything the COM API can reach.

Signal heads and detectors, by contrast, are ordinary network objects and fully editable for every controller type.

DoDetect controller type on model upload and set expectations accordingly. A practical v1: pre-build alternative signal programs in the editor and let the agent switch between them, rather than authoring timings.
03Fragile references

Identifiers that don't mean what they look like

Vissim's object graph is held together by numbers, positions and ports — several of which move, get reused, or point at things outside the model file.

Conflict area numbers are not stable identity

silent

Numbers come from a counter as overlaps are discovered and are never reissued when one is destroyed. PTV's own shipped roundabout example has 55 conflict areas numbered up to 71 — sixteen permanent gaps from its editing history.

DoKey on the unordered pair of link numbers, never on the conflict area's own number.

Positions are measured from the link's start

silent

Signal heads, detectors, routing decisions, speed decisions and priority rules are all anchored by a distance from the beginning of their link. Extending a link upstream moves every one of them relative to the intersection — the stop line stays put in the data and slides in the world. The detector-to-stopline distance that governs actuated signal timing is computed, not stored, so it changes with no attribute changing.

DoTreat any edit to a link's start point as invalidating every positioned object on it; recompute and present the resulting shifts.

Splitting a link renumbers it and inserts a gap

silent

The split produces a new link with a new number for the second half, breaking every route that referenced the original. It also physically inserts a gap centred on the split point — the geometry actually changes, not just the data structure.

DoAvoid splits where possible; where unavoidable, treat them as a full snapshot-and-reconcile operation.

Port numbers bind detectors to external controllers

silent

Actuated controllers address detectors by port number, not by the detector's object number. Renumbering ports silently rewires which detector calls which movement — the model runs, the signals respond to the wrong loops.

DoTreat port numbers as immutable. Same for signal group numbers, which are the join key to external controller files — PTV warns explicitly that changing them can make the model incompatible with its controller files.

Deletes cascade, and the documentation is vague about how far

silent

PTV says only that deleting an object means other objects positioned on it "may also be deleted," without enumerating which. Deleting a routing decision definitively takes all its routes with it.

DoEnumerate everything attached to an object before deleting it, and show the user the full blast radius. Copy-on-write scenarios make this recoverable.
04Domain semantics

Rules an algorithm has to encode

These aren't bugs or fragility — they're the domain's actual logic. Getting them wrong produces answers that are wrong in ways only a traffic engineer would catch.

Volume is always per hour, whatever the interval

domain

PTV: "You must always enter the number of vehicles per hour, even if the time interval is shorter." A user asking for 300 vehicles in a 15-minute peak needs the value 1200 written.

DoAlso remember demand is defined per time interval — a model with a four-interval morning peak has four values per input, and scaling traffic means scaling all of them.

"More trucks" redistributes rather than adds

domain

Vehicle mixes are stored as relative shares normalised to 100%. Raising the truck share lowers the car share — the total stays the same. If the user means "more trucks and the same number of cars," the total volume must rise too.

DoAsk which they mean. Both are legitimate and they produce very different results.

Scaling demand automatically scales routes — don't do it twice

domain

Route volumes are relative shares of what arrives, so raising input volume by 20% automatically carries through to every downstream route. An agent that also scales the route flows corrupts the turning proportions.

DoScale inputs only. Leave relative flows alone.

Cycle time is a corridor property, not an intersection one

domain

Coordinated signals stay in step only while they share a cycle length — Vissim derives each controller's position in its cycle from an absolute clock. Change one intersection from 90 to 100 seconds and the green wave along the whole corridor dissolves within a few cycles. Nothing in Vissim flags this; there is no corridor-level object that would notice.

DoTreat cycle time as a network-scope edit affecting every coordinated controller, never as a single-intersection change.

Splits must sum to the cycle, and include the clearance

domain

In ring-barrier controllers, the splits in each ring must add up to the cycle length — lengthening one without shortening another is arithmetically invalid. And a split covers green plus yellow plus red clearance, so an agent treating a split as green time systematically over-allocates.

DoEncode the sum constraint and the minimum-green floors as hard checks before submitting any timing change.

Restrictions apply per vehicle class, not per type

domain

Vissim has three levels: category (a fixed built-in list), type (technical characteristics), and class (a grouping used for restrictions, speed assignment and evaluations). Speed decisions, lane closures and route validity are all defined per class — and any class not listed keeps its original behaviour, so a partial specification silently exempts everyone else.

DoEnumerate the classes present in the model and require an explicit answer about which ones an edit applies to.

Units and percentages come back unmarked

silent

Whether speeds are km/h or mph is a network-level setting stored in the model file, and values come across the API in whatever the model uses, with nothing in the value to say which. Separately, percentages arrive as 0–1 rather than 0–100 — writing 45 where 0.45 was meant produces silent nonsense.

DoRead the unit settings once on upload and stamp them onto every value that reaches the dashboard. Never compare numbers across models without normalising.
05Results

You can only answer what was armed before the run

This is the hardest constraint on a conversational dashboard, because it limits what the assistant can answer at all — not how it answers.

Evaluations are not retroactive

blocks

Vissim keeps no general simulation history. It records only into the measurements you switched on before starting. If nobody configured an evaluation at the intersection the user is asking about, that number does not exist and cannot be recovered — you must configure it and re-run.

DoParse the model's evaluation configuration on upload and build a manifest of what it can answer. Sort every question into answerable / answerable-with-caveats / requires-a-re-run, and say plainly which.

Adding an evaluation deletes the results you already have

blocks

Vissim discards previous simulation results when the evaluation configuration changes or when the network objects an evaluation depends on are edited. Setting up to answer a new question therefore destroys the answers to the old ones — potentially a multi-hour batch of runs.

DoGuard this path explicitly in the UI. Never let an agent add an evaluation without warning what it will erase.

Warm-up is not a setting — it's a field on every evaluation

silent

Simulations start with an empty network, so early results are meaningless. There is no warm-up checkbox: you exclude it by setting a start time on each evaluation individually, and the default is zero. It's entirely possible for one evaluation to be correctly windowed and another left contaminated. DOT minimums range from 10 to 30 minutes.

DoRead every evaluation's start time and warn on any that begins at zero.

"Queue length" is not a portable number

domain

What counts as queued is defined by configurable speed thresholds and a maximum gap between vehicles — and the reported value is also truncated by wherever the next counter upstream sits. Two models of the same junction with different settings produce genuinely different queue numbers. The reported average also includes the zeros, so a movement that queues badly for a tenth of the interval averages out to nearly nothing.

DoAttach the queue definition and counter location to every queue answer, and refuse to compare queues across models configured differently.

Delay is only counted from a fixed distance upstream

silent

Intersection delay is measured from a configurable point upstream of the junction, default 100 metres. When queues stretch further back than that, the excess delay simply isn't counted — so the most congested intersections are the ones whose delay is most under-reported.

DoCompare queue length against the delay-segment start and flag results where the queue exceeds it.

The averaging interval changes the answer

domain

Results are aggregated into intervals fixed at configuration time. Hourly and two-minute averages of the same run are different numbers, and peaks vanish into long intervals. Washington State adds a subtle one: the interval should not be a multiple of the signal cycle length, or you sample the same point in the cycle every time.

DoReport the interval alongside every number.

One run is not an answer

domain

Microsimulation is stochastic; a single run is one draw from a distribution. DOT minimums: Maryland 5 runs, Oregon 10, Washington State 11. Vissim can run and average multiple seeds natively.

DoDefault to multiple seeds, report the mean with its spread and the run count, and flag any single-run result as provisional.
The one escape hatch worth building around

Vissim can write a full vehicle trajectory record — every vehicle's position and speed at every timestep. It is the only output from which other measurements can be reconstructed after the fact: delay, queues, travel time, density, anywhere in the network, at any interval, under any queue definition. Vissim won't backfill its own evaluations from it, but your own post-processor can. A model instrumented this way is retroactively queryable; one without it is not. The cost is file size, so it needs an attribute subset and sensible filters — but this single decision converts a large class of "I'd have to re-run" answers into ordinary ones, and it is the strongest architectural lever available for the conversational experience.

06Calibration

Editing a signed engineering deliverable

A calibrated model is a tuple — geometry, demand, control, behaviour parameters, seed count and warm-up — that jointly reproduces observed traffic within agency tolerances, documented in an approved report. PTV's own warning: change driving behaviour parameters "only if you are a very experienced user."

Driving behaviours are global objects

silent

A behaviour parameter set isn't attached to a link — it's a shared object that many links point at. Editing one to fix a single ramp changes every link in the network using it. There is no per-link containment. This is why Maryland's DOT ships fourteen separately-named behaviour sets rather than editing shared ones.

DoNever edit a shared behaviour in place. Duplicate it, edit the copy, and retarget only the intended links — the same rule human modellers are given.

Capacity is many-to-one in the parameters

domain

Published sensitivity work found multiple distinct parameter combinations producing identical capacity. So "restore this parameter to its default" doesn't restore the model — it moves it to a different point where the engineer's compensating adjustments no longer make sense. Parameter-level diffs aren't semantically meaningful in isolation.

DoRecompute the calibration statistic after any change and refuse to persist an edit that moves the model outside its agency criteria without explicit sign-off.

Some parameters are off-limits by agency policy

domain

Washington State and Maryland both publish tables of which parameters may be adjusted and within what range — and both say of the deeper car-following parameters simply "use default." Washington State requires written justification and approval for anything outside the suggested ranges.

DoEncode these as hard blocks, not warnings. An AI has no field data justifying a change an agency requires evidence for.

A version upgrade alone can change results

silent

PTV's release notes state directly that lane-change behaviour, merging and conflict-area handling changed in the 2024 version and that "simulation results can differ to those of previous versions." A merging option that some models had switched off no longer exists and is now always on. A calibration can therefore break without anyone editing anything.

DoPin the Vissim version per deployment, record it with every result, and re-validate calibrations on any upgrade.
07Operations

Running Vissim on a server, unattended

Vissim is a desktop application being asked to behave like a service. Most of these are solvable, but they need designing for rather than discovering.

Dialogs will hang a worker forever

blocks

The single biggest automation risk, and mostly undocumented. An empty file path opens a file browser and blocks the call indefinitely. Saving a model authored in an older Vissim version prompts about format conversion. Saving where a results folder exists prompts again. Runtime warnings pop a message window. There is no global "suppress all dialogs" switch.

DoValidate every path before use, pre-set the format-conversion preference on the server image, enable quick mode (which suppresses the message window), and run every job in a child process under a wall-clock watchdog that kills and relaunches.

Vissim cannot run as a Windows service

blocks

PTV states it "always uses a window handle and needs to run in a user session." It also needs a floating network licence — single-user licences fail over remote desktop on server operating systems. Concurrency is capped at roughly four instances per session, each consuming licence capacity.

DoPlan for a persistent logged-on interactive session that is disconnected but never logged off, and size the fleet around four workers per session. This is a licence-cost and capacity-planning input, not just an engineering detail.

The naive loop is the slow one

domain

The API is an out-of-process server, so every property read crosses a process boundary. Reading five attributes from a thousand vehicles one at a time is five thousand round trips; the batch methods do it in one. Quick mode and suspending the interface redraw are separate, complementary wins.

DoUse the batch attribute methods from the start, and read bulk results out of the results database rather than through the API at all.

The error file is overwritten between runs

silent

With a single run configured, each new simulation overwrites the previous error file — the record of removed vehicles and unmet demand from the last run disappears when you start the next.

DoSweep and archive the error file per job before the next run starts.

Simulation resolution changes results, not just runtime

silent

PTV: "simulations using different simulation resolutions produce different results." Values below 5 steps per second are explicitly unsuitable for final results.

DoLock resolution across any set of scenarios intended for comparison, and never let it be tuned for speed on a run whose numbers will be reported.
08What this means to build

The validation layer, specified

Nearly every item above resolves into the same small set of mechanisms. Build these and the catalogue is mostly handled; skip them and each entry becomes a separate bug found by a customer.

  1. A model manifest, built on upload. Parse the model once and record: Vissim version, unit settings, controller type per intersection, which evaluations are armed and with what windows and intervals, whether dynamic assignment is in use, which driving behaviours exist and which links use them. This manifest is what the assistant is allowed to promise.
  2. A reference registry around every mutation. Before an edit, enumerate everything attached to the objects being touched; after, assert each one landed somewhere valid. This is the same mechanism that powers undo, the diff view, and the "what will this affect?" preview.
  3. A rule table that lives in code, not in the prompt. Range checks, the splits-sum-to-cycle constraint, intergreen validation, off-limits parameters, model-type matching. A prompt is a suggestion; a check is enforcement.
  4. Post-run assertions on every result. Latent demand still zero, removed-vehicle count unchanged, no passive conflict areas added, throughput conserved, no previously-flowing link now at zero. Run a short smoke simulation before committing to the full multi-seed batch.
  5. Golden test models in the repo. Small networks with known-correct outcomes for each supported edit, run on every change to the core library. This is the difference between a library people trust and one they don't.
  6. An answerability router. Every question sorted into answerable now, answerable with caveats, or needs a re-run — with the caveats attached to the number rather than buried.
  7. Provenance on every figure. Interval, warm-up window, seed count, units, queue definition. Not decoration: it is what lets an engineer trust a number the AI produced, and what settles a dispute six months later.
The strategic read

This catalogue is why the Vissim version of conversational simulation hasn't been published while the SUMO versions have. SUMO's file formats are open, documented, and forgiving; Vissim is a closed commercial product whose data model actively hides these couplings. That makes the work harder — and it also means the validation layer, not the AI, is the defensible asset. It is the encoded expertise of Dochak's traffic engineers, and it is exactly the thing that cannot be reproduced by someone who has only read the API documentation.
